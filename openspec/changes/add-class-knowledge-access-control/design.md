# Design

## Context

项目目前只有 OpenSpec 配置和 README，没有既有应用、数据模型或运行时可复用。本设计采用 Flask、SQLite 与 Docker Compose 实现单体 Web 应用；行为契约见三个 delta specs。

## 本次更新记录

### 新增

- 记录后续检索变更在既有 Compose 基础上加入 MySQL、Qdrant、OpenAI API Key 与两个独立 MySQL 密码。
- 记录 MySQL 持久卷的首次初始化与显式密码轮换要求。

### 删除或替代

- 替代将 Compose 描述为仅包含应用与 SQLite 持久卷的运行时假设；SQLite 主数据设计和本变更的认证边界不变。

## Goals / Non-Goals

**Goals:**

- 让所有受保护页面和 API 先完成身份验证，再由服务端统一执行角色与班级授权。
- 将用户、班级、材料及知识库记录的关联持久化，保证上传成功后可从同班材料列表查询。
- 以 Flask 和 SQLite 提供一个可在 Docker Compose 中运行的最小可验证实现。
- 以容器化启动、环境变量注入秘密，并提供可用于编排器的轻量健康探针。
- 为自动化测试提供明确的成功、未认证、无角色权限和跨班级拒绝路径。

**Non-Goals:**

- 不在本变更中实现注册、找回密码、单点登录、管理员后台或角色自定义。
- 不定义跨班级共享、教师代课/多班管理的产品界面；数据模型保留多班成员关系的扩展空间。
- 不包含文件病毒扫描、全文检索、知识问答或材料版本管理。

## Decisions

### Flask 会话与密码哈希

Flask 通过受签名、`HttpOnly`、具备合理有效期的会话 Cookie 保存最小的 `user_id`。应用启动时从服务器环境变量 `AUTH_SECRET` 读取 Flask `SECRET_KEY`；变量缺失即失败。每个受保护请求都从 SQLite 重新加载用户、角色和班级成员关系，页面路由未认证时跳转到登录页，API 未认证时返回 401。

密码使用 Werkzeug 的密码哈希函数（优先采用安全的默认 `scrypt` 参数）生成和校验，`users` 表只包含 `password_hash` 而不包含明文密码。请求、异常与调试日志不得记录密码、哈希或 `AUTH_SECRET`。选择 Flask 内建会话和 Werkzeug 哈希可保持课程项目依赖最小；浏览器可读 JWT 会扩大泄露面，完全依赖前端路由无法保护直连 API，均不采用。

### Flask + SQLite 的数据模型与预置数据

SQLite 数据库包含 `users`、`classes`、`class_memberships`、`materials` 与 `knowledge_base_records`。`class_memberships` 使用户与班级的关系显式化，既支持当前的本班访问，也避免把未来多班教师能力锁死在单一 `class_id` 字段中。`materials` 与 `knowledge_base_records` 都携带 `class_id`，并以 `material_id` 建立关联。`materials` 额外保存已验证的 UTF-8 `content_text`，原始文件仍保存于上传目录；二者共同构成可再次打开的材料。

初始化命令在空数据库中创建 Class A、Class B、Class A 教师、Class A 学生和 Class B 学生。预置账户的密码经同一哈希流程写入；用于开发/测试的初始明文密码只从运行时输入或环境配置取得，绝不保存至数据库或版本库。SQLite 适合本课单实例与 Compose 挂载卷的目标；生产数据库、复制与 HA 是非目标。

### 服务端班级过滤与角色决策

所有材料入口按同一顺序执行：认证 → 加载角色与成员关系 → 校验目标班级或材料的 `class_id` → 执行业务动作。上传入口额外要求教师角色，否则直接返回 403。列表查询从服务端认证上下文导出允许的班级范围，并在 SQLite 查询的 `WHERE` 条件中强制过滤；单条材料先查询所属班级再做成员校验。显式请求无成员关系的班级或材料时返回 403，响应中不包含其他班级的材料内容或元数据。

客户端传入的 class ID 仅用作待校验目标，绝不作为授权依据。前端隐藏上传按钮只改善体验，不能替代后端角色和班级验证。

### 上传与知识库写入数据流

教师上传材料时，Flask 先验证会话、教师角色和目标班级成员关系，再校验安全文件名、扩展名（仅 `.txt`、`.md`，不区分大小写）和 10 MB 大小上限。应用将文件读取为 UTF-8 正文；无法解码的输入以 HTTP 400 拒绝。通过校验的文件写入临时路径，随后在一个 SQLite 事务中创建含 `content_text` 的 `materials` 和关联的 `knowledge_base_records`；事务成功后将临时文件发布到应用数据目录。任一环节失败时回滚数据库并清理临时文件，避免出现可查询的半成品记录。材料列表只读取认证用户有成员关系的班级记录，因此成功上传后同班师生都可查询到对应知识库记录。

材料正文查看页和下载接口均先按材料 ID 查询所属班级，再校验当前成员关系；正文以转义后的纯文本展示，Markdown 不渲染为 HTML。删除接口额外要求教师角色和目标班级成员关系；删除成功时同时移除原文件、材料记录和关联知识库记录。文件删除使用临时改名配合数据库事务：数据库操作失败时恢复原文件，提交后再清理临时文件，降低文件与记录不一致的风险。

本课将文件存储在 Compose 持久卷的应用数据目录中，不接入对象存储。未来接入外部存储时，仍需保留临时上传、事务提交和失败清理语义。

### Docker Compose 与 `GET /health`

提供应用 Dockerfile、`compose.yaml`、`.env.example` 和忽略规则。初始应用通过环境变量传入 `AUTH_SECRET`，并挂载持久卷保存 SQLite 数据库和上传材料；后续 `knowledge-retrieval` 变更将 Compose 扩展为应用、MySQL 与 Qdrant，并增加 `OPENAI_API_KEY`、`MYSQL_PASSWORD` 和独立的 `MYSQL_ROOT_PASSWORD`。示例文件仅列占位变量，不提供真实密钥；全部秘密仅由服务端读取。MySQL 持久卷首次初始化后，修改 `.env` 本身不会轮换数据库账户密码，必须保留原值或在备份后执行显式运维操作。服务启动时先验证必需配置并初始化数据库。

`GET /health` 不需要认证；它执行最小 SQLite 可读性检查，在可提供服务时返回 HTTP 200 和状态 JSON。Compose 的 healthcheck 调用该端点。若数据库不可用，端点返回失败状态，使容器不会被误报为健康。

## Risks / Trade-offs

- [共享的班级会话或遗漏任一入口的授权校验] → 将认证、角色和班级验证封装为 Flask 装饰器/策略，并对每个入口写直接 API 测试。
- [上传文件与数据库事务无法形成真正原子操作] → 采用临时对象、事务提交后发布和失败清理，并在测试中覆盖持久化失败。
- [会话密钥缺失或泄露] → 启动时校验必填环境变量，使用 `.env.example` 仅列变量名，并禁止秘密写入日志或版本库。
- [错误响应泄露其他班级资源存在性] → 统一返回不含材料内容、元数据或知识库记录的拒绝响应；安全测试验证响应体。
- [SQLite 文件在容器重建后丢失] → 将数据库和上传目录挂载到 Compose 持久卷，并用重启后的查询测试验证。
- [健康端点在依赖不可用时错误报告健康] → 健康检查执行最小 SQLite 可读性验证，并为 Compose 配置重试间隔和启动宽限期。

## Migration Plan

1. 建立 Flask 应用、SQLite schema、预置数据命令与 Compose 持久卷；在部署环境提供 `AUTH_SECRET`。
2. 部署认证、会话、成员关系和材料/知识库持久化，同时启用健康检查。
3. 使用预置教师、学生及 A/B 班数据验证登录、403 上传拒绝和跨班拒绝，再导入真实数据。
4. 回滚时停止新应用版本并恢复 SQLite 数据库与材料卷的兼容备份；绝不将密码哈希降级为明文或导出会话秘密。
